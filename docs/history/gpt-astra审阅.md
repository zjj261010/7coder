## 四、问题详情与对应措施

### AST-01｜只读 Git 工具存在 shell 注入

**位置**：`D:\ai-workspaces\7coder\index.js:329–337,1774–1778,1801–1808,1833–1836`。

**根因**：`git_diff_tool` 在自动安全工具清单中，但路径参数经 `JSON.stringify` 后拼入命令字符串，最终交给 `execSync("git " + args)`。JSON 字符串转义不是 cmd/sh 参数转义。提交信息也使用了相同模式。

**复现**：在新建的隔离 Git 仓库中，以 `default` 权限调用 `git_diff_tool`，传入带引号和命令分隔符的虚构路径；工具没有请求人工批准，却实际创建了无害标记文件。Node 24 与 Node 13 都出现 `markerCreated: true`。

**影响**：模型的一次“只读 diff”调用即可变成 shell 执行，而且这条路径不经过 `run_command` 的危险命令检查。此项不依赖 HTTP 对外开放。

**措施**：

1. Git 适配器只接受参数数组，例如 `execFile('git', ['diff', '--', normalizedPath], { shell: false, cwd })`。
2. 同时修复 commit、worktree 等所有 Git 调用；不要只对单个危险字符加黑名单。
3. 显式固定工作目录和允许的子命令；用户输入只能作为参数值，不能成为命令片段。
4. 在实现改好前，不再把能够触发 shell 解析的 Git 调用标为自动只读安全操作。

**验收**：路径/提交信息覆盖双引号、空格、`&`、`%`、美元符号、反引号等；它们只能成为参数或被拒绝，不能创建探针标记。Windows 和 POSIX 分别验证。

### AST-02｜文件自动放行规则可绕过 `.env` 审批

**位置**：`D:\ai-workspaces\7coder\index.js:477–501,2095–2107`。

**根因**：`write_file` 只要原始路径字符串包含 `7coder.md` 就走自动执行分支；该分支排除了 `protectedRead`，却没有排除 `protectedWrite`。后续路径规范化才决定真正写入哪里。

**复现**：在 `default`、非交互上下文中，直接写 `.env` 返回拒绝；改成测试输入 `7coder.md/../.env` 后返回 `Written: .env`，隔离目录中的原始内容被覆盖。全程未给出审批。

**影响**：安全判断依据的字符串和实际文件目标不一致。类似命名的普通代码路径也可能得到超出预期的自动写入权限。

**措施**：

1. 先解析并规范化真实目标，再统一计算保护级别和审批策略。
2. 移除 `includes('7coder.md')`；若保留自动日志特例，只允许工作区根目录中规范化后精确匹配的 `7CODER.md`。
3. 保护规则优先于一切自动放行分支；模式差异只能改变“需要审批还是拒绝”，不能绕开检查。
4. 文件别名、内部链接、路径大小写及目录穿越表达式应进入同一套策略测试。

**验收**：直接路径、规范化等价路径和链接别名访问同一目标时得到相同权限结论；`default` 无审批不能写受保护文件。

### AST-03｜工作流审批没有真正批准任何步骤，且状态跨请求共享

**位置**：`D:\ai-workspaces\7coder\index.js:260–274,1683–1712,2137–2152,2179–2189`。

**根因一：自动审批闭环缺失。** `auto` 模式对 `workflow_tool` 外层直接放行；进入后增加 `workflowStepDepth`，内层又以“继承计划审批”为由跳过轻模型检查。实际并不存在经过批准的计划。

**根因二：全局权限状态泄漏。** `workflowStepDepth` 是进程全局变量，另一个请求也会看到非零深度。`subAgentModeOverride`、`agentDepth` 同样是全局状态，建议一并审计，而不是只修复审批桥对象。

**复现**：

- 将自动审批模型设为始终拒绝，普通写文件被拒；同样的写文件放进 workflow 却成功。
- 工作流执行短暂异步等待期间，另一会话的写文件调用被放行，并真实落盘。

**影响**：`auto` 在复合工具路径上退化为近似直接执行；并发会话的权限状态不隔离。现有 `approval-iso` 测试通过，只能证明它覆盖的审批桥场景，不能证明整个权限上下文隔离。

**措施**：

1. 二选一：逐步审批，或先审批完整且不可变的计划；不能“外层不审批、内层继承”。
2. 如继承审批，传入明确的授权对象，绑定 runId、步骤摘要和批准范围，而不是靠深度计数器表示授权。
3. 新建请求级 `ExecutionContext`，显式传递权限模式、父授权、工作流深度、代理深度、审批桥、取消状态。
4. 先用显式参数实现，避免为此立即做全量模块重构；与 Node 13 的兼容要求保持一致。
5. `executeToolRaw` 的已批准分支也应统一透传上下文，避免遗漏第 4 个参数形成新的路径差异。

**验收**：拒绝模型下 workflow 不能偷偷执行；A 的 workflow/agent 挂起时，B 的权限不变；拒绝/取消一个请求不会批准或取消另一请求。

### AST-04｜密钥保护只覆盖少数文件名，结果日志会再次泄露

**位置**：`D:\ai-workspaces\7coder\index.js:158–182,202–219,490–501,1078–1090,1833,2071–2079`；`D:\ai-workspaces\7coder\.gitignore`。

**根因**：

- 模型配置文件允许保存 `apiKey`，但不在受保护目标清单中。
- `read_file` 对这类文件自动执行。
- 审计只处理 `entry.args`，直接保存工具结果首行；首行可能就是密钥 JSON。
- 项目忽略规则未覆盖模型密钥文件和多数运行产物；`git_commit_tool` 默认执行 `git add -A`。

**复现**：在隔离配置文件中放入虚构密钥，`default` 模式下直接读取得到密钥，审计文件也包含相同虚构密钥。未读取或外传真实凭据。

**影响**：用户许可“本机设置页面可显示密钥”，不等于许可模型自动读取密钥或把密钥写入长期日志。默认全量暂存还可能把配置、会话和日志带入提交；本轮未将真实秘密提交或推送。

**措施**：

1. 至少保护安装目录与工作区的模型配置、凭据文件、相关备份和日志；建议使用统一路径策略，而非不同工具各自维护零散列表。
2. 对模型提供配置元信息时，只返回 endpoint、模型名和 `hasKey` 等字段，不返回密钥值。
3. 敏感文件内容默认不进入工具结果；审计结果、异常摘要与请求元数据都应采用字段白名单和脱敏规则。
4. Git 提交前列出将提交的文件并检查敏感路径；默认仅提交明确选择的业务文件，避免自动 `add -A`。
5. 完善忽略规则，但保留可能需要共享的 skills；不要用“一刀切忽略整个配置目录”代替分层设计。

**验收**：虚构密钥不得出现在模型工具结果、审计结果和待提交文件中；明确授权读取敏感文件的行为仍需可追踪。

### AST-05｜下载失败会删除原文件

**位置**：`D:\ai-workspaces\7coder\index.js:1230–1262`。

**根因**：下载开始前就确定 `dest`，任何异常都尝试删除它。上游返回错误时，写入流可能尚未建立，但已有目标文件仍被删除。成功建立流后也直接覆盖原文件，没有事务边界。

**复现**：目标文件预先写入 `ORIGINAL`，本地 HTTP 服务返回 503；调用后得到 `Download error`，同时 `originalExists: false`。两个运行时一致。

**影响**：一次失败的下载就可能损坏既有工作区内容，不需要攻击者，也不依赖特殊权限模式。

**措施**：

1. 下载到同目录、唯一命名的临时文件；仅清理本次创建的临时文件。
2. 接收完整且校验成功后再替换目标；覆盖已有文件前进入备份/审批流程。
3. 失败、超限、取消时同时关闭远端流和本地 writer，避免句柄遗留或继续写盘。
4. 对 Windows 的目标已存在、文件占用等替换行为单独实现并测试；失败应保留旧文件。

**验收**：503、断网、超限、磁盘错误、取消后原文件哈希不变；成功覆盖可恢复；没有残留活动流。

### AST-06｜新建 Web 会话永远不会首次保存

**位置**：`D:\ai-workspaces\7coder\webui.html:342–343,401–411,544–548,734–740`。

**根因**：新会话的 `sessFile` 初始化为 `null`，而 `autoSaveSession()` 在 `!sessFile` 时直接返回；设置它的路径依赖加载一个已经存在的会话。这形成首次保存的循环依赖。

**复现**：使用原始函数、非空 user/assistant 历史和 `sessFile = null`，观察到 `fetchCalls: 0`。后端保存接口可用，并不能弥补前端根本不发请求。

**影响**：首次使用或点击“新对话”之后的聊天没有完整持久化；刷新/关闭时可能丢失。后台摘要文件不是完整会话的替代品。

**措施**：

1. 允许首次不带文件名保存；收到响应后调用统一的 `rememberSessFile` 同时更新内存和本地记录。
2. 将 `autoSaving` 布尔开关升级为串行保存队列/dirty 标记，避免上一次保存进行中时静默丢弃下一次更新。
3. 保存请求绑定会话 ID/版本号；切换会话后，旧请求不能修改当前会话的文件名。
4. UI 显示“未保存/保存中/已保存/失败”，保存失败应可重试。

**验收**：干净目录首聊、点击新对话、快速连发、保存中切换会话、失败重试后刷新，历史均正确恢复；补真正的浏览器测试。

### AST-07｜SSE 业务错误会被吞掉

**位置**：`D:\ai-workspaces\7coder\webui.html:501–544`；`D:\ai-workspaces\7coder\index.js:3144–3150`。

**根因**：前端遇到 `j.error` 会抛错，但紧接着的 catch 只有在错误文案包含 `upstream` 时才重新抛出。因此 `API error 401 ...`、`Max retries reached.` 等合法业务错误会被当作可忽略内容。

**复现**：将包含 401 错误的 SSE JSON 送入原始解析片段，`propagated: false`。请求可能走“完成”分支而不是错误分支。

**影响**：用户看到空回复或半截回复，却不知道真实失败原因；失败内容还可能被当成正常会话保存。

**措施**：把 JSON 解析异常与服务端业务错误分开处理；只忽略明确允许忽略的非业务帧。对 `j.error` 一律抛出类型化错误；保留已生成内容，并标记“不完整/失败”，而不是直接删除整个回复气泡。

**验收**：401、429、超时、重试耗尽、上下文超限、损坏 JSON、用户取消分别进入正确 UI 状态，不依赖错误文案中的某个英文单词。

### AST-08｜设置接口可把换行写成额外环境变量

**位置**：`D:\ai-workspaces\7coder\index.js:2914–2925,3162–3178`。

**根因**：设置接口只检查字符串类型，写入时直接拼接 `KEY=value`。值中的换行可变成新的配置行；同时运行时全局变量先被修改，随后才写磁盘。

**复现**：通过真实本地设置接口提交虚构 API key，其中包含换行及 `PERMISSION_MODE=bypass`，服务返回 200，隔离配置文件出现独立的权限变量行。**本轮验证的是配置注入落盘，没有把“已重启并完成权限提升”当成已执行的测试。**

**影响**：一次设置更新可意外改变其他配置；写盘失败时则可能出现“接口报错但运行时已切换”的不一致。这与是否允许本机免鉴权是不同问题，即便配置了鉴权也需要做输入校验。

**措施**：

- endpoint、模型名、API key 按业务约束校验，拒绝不允许的 CR/LF/NUL；endpoint 校验协议和 URL 结构。
- 仅重写受管键；正确处理 dotenv 支持的引号和值，不重新解释无关配置。
- 先形成候选配置、验证、原子持久化，再一次性切换内存；失败保留旧状态。
- 当前请求使用启动时的配置快照，避免处理中途切换上游造成混用。

**验收**：换行注入返回 400 且文件不变；含特殊字符的合法值可 round-trip；模拟写入失败时全局配置不改变。

### AST-09｜同步命令阻塞 HTTP；取消未贯穿活动操作

**位置**：`D:\ai-workspaces\7coder\index.js:934–1000,1143,1158,1175,1759,2317–2370,3082–3113`。

**静态发现**：

- 多条执行路径使用 `execSync`/`execFileSync`，单次允许运行数分钟；HTTP 也在同一进程。
- `cancel` 在工具循环边界检查，但没有传给活动中的 axios 请求、同步子进程或子代理运行。
- 非流式 HTTP 路径未传取消回调。
- 审批桥清理位于正常返回路径；异常和断连的资源清理缺少统一 `finally`。

Node 官方文档明确说明同步子进程调用阻塞事件循环；因此“工具函数写成 async”并不能令内部同步调用变成非阻塞。[W2]

**影响**：一次长任务可能阻止健康查询、其他会话、审批与取消被及时处理；用户点击停止，不代表上游计费请求已经停止。此前修复的“边界取消”仍有价值，但不能表述为完整的活动请求取消。

**措施**：使用异步 `spawn`/`execFile`，逐块读取且限制输出；为 axios、子进程、审批等待和子代理显式传递取消信号；基于所用 axios/Node 版本实现兼容的取消适配器；用 `try/finally` 清理计时器、桥与句柄。Windows 子进程树处理需要单独验证。

**验收目标（建议值，非本轮测量值）**：后台命令执行期间，本地健康请求通常在 200ms 内返回；取消后在约 1 秒内发出上游/子进程终止动作；多次失败和取消后无遗留审批与计时器。

### AST-10｜请求体限制只限制响应结论，没有限制内存累积

**位置**：`D:\ai-workspaces\7coder\index.js:2736–2993,3024–3038`。

**根因**：聊天接口超过阈值后仅设置 `oversized = true`，仍持续 `body += chunk`，直到 `end` 才返回 413；其他多个 POST 接口没有同等上限。长度计算用字符串字符数而非接收字节数。

**影响**：大请求和多个慢请求仍能持续占用内存；最终返回 413 不能证明资源已经受控。同步解析和同步会话读写会进一步放大延迟。

**措施**：统一 body reader；在接收阶段按字节计数，超限立即停止累积并安全结束请求；配置按接口区分的 body 限额、请求超时和并发上限。会话列表提供分页和摘要索引，避免每次全量读取完整历史文件。

**验收**：超过上限后不再累积后续字节；客户端不结束上传也能被及时拒绝；覆盖多字节中文、无 Content-Length、慢上传、并发上传。压力测试应验证 RSS 峰值，而不仅检查状态码。

### AST-11｜工具失败状态靠文本猜测，导致错误被标成成功

**位置**：`D:\ai-workspaces\7coder\index.js:1703–1712,2073–2079,2092–2093`。

**复现一**：工作流第一步 `list_dir` 访问不存在目录，返回 `List error`；工作流未把它识别为失败，继续执行下一步写文件，最后返回 `[OK] Workflow complete`。对照 `Edit error` 则会停止。

**复现二**：`denial` 模式拒绝写入，返回 `Permission mode = denial. Action blocked.`，审计却记录 `status: "ok"`。

**影响**：调用方、模型和用户不能可靠区分成功、失败、拒绝、取消；依赖前置步骤的后续操作可能在条件未满足时继续执行。

**措施**：

1. 内部采用结构化 `ToolResult`，至少包含 `status`、`code`、`message`、`data`、`retryable`。
2. UI/模型边界再渲染为文本；工作流和审计消费结构化状态，不用正则猜首行。
3. 明确 optional 步骤失败的处理方式，并在最终结果中区分“完全成功”和“部分成功”。
4. 渐进迁移：先给高风险工具和工作流套适配层，再逐步统一其他工具。

**验收**：所有工具的失败、拒绝、取消都能映射到统一状态；非 optional 失败停止后续写操作；审计不把 denial 记为成功。

### 5.1 免鉴权本机服务：维持“待重新决策”，不擅自推翻

历史记录的 P0-4、OPT-2 已明确接受本机明文设置接口和不强制设置 HTTP key。本轮不把“必须新增登录系统”作为默认整改要求。

若未来重开此决策，可先做低摩擦措施：校验 Origin/Host、拒绝不需要的 simple content types、为状态变更使用 CSRF token/本地会话凭证、非 loopback 启动时强制显式确认。OWASP 的 CSRF 指南是相关设计依据。[W3]

**边界声明**：loopback 绑定是网络暴露控制，不应作为完整的浏览器请求来源认证。对个人单机使用是否接受剩余风险，由用户决定。

### 5.3 传统运行时：保留兼容目标，但明确安全边界

截至本次审阅日期，Node 13 已在官方 EOL 范围内；旧版本“能运行”与“仍获得官方安全维护”是两个不同维度。[W1]
